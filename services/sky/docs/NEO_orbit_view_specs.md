# Specs: NEO/NEOCP Visualization Roadmap (v1)

Context: текущие датасеты уже содержат достаточно полей, чтобы начать визуализацию “сцены пролёта” и sky-track. Полноценная орбита потребует добавления орбитальных элементов (SBDB) либо state vectors (Horizons/SPK).

---

## Spec 1 — NEO Encounter View (Earth-centered snapshot + short track)

Цель: для **confirmed NEO (CAD bucket 10LD/… )** показать “схему пролёта” относительно Земли. Это НЕ кеплерова орбита вокруг Земли, а геоцентрическая геометрия (вектор положения и, опционально, короткий трек на заданном окне времени).

### Пользовательская ценность
- Быстро понять: где объект “находится” относительно Земли в момент close approach, насколько близко, и где он на небе для наблюдателя.

### Входные данные (уже есть)
Из `alerts_neo.json` по item:
- `meta.t_utc_iso` (момент события)
- `meta.dist_au` и/или `meta.dist_ld` (расстояние)
- `ra_deg`, `dec_deg` (положение на небосводе)
- опционально: `meta.v_rel_km_s`, `meta.alt_deg`, `meta.az_deg`
- `id`, `title`

### Доп. данные (опционально, но рекомендуется)
- `de421.bsp` (или аналог) + leap seconds kernel (для строгой ET/UTC); используется только для референса/подписей, не обязателен для геоцентрической картинки.
  - Если SPICE не подключаем на первом шаге, работаем в упрощённой геоцентрической инерциальной системе: Earth-centered, axes = equatorial (ICRF-like).

### Вычисления
1. Преобразование сферических координат в декартовы:
   - r = dist_au (AU)
   - α = ra_deg, δ = dec_deg
   - x = r * cos(δ) * cos(α)
   - y = r * cos(δ) * sin(α)
   - z = r * sin(δ)
2. (Опционально) “скоростной” вектор:
   - Если нет направления скорости, используем только модуль `v_rel_km_s` в подписи.
   - Если добавим 2–3 дополнительные точки (см. ниже), можно оценить направление по разности координат.

### Рендер (минимум)
- 2D view в плоскости XY (equatorial) + отдельный “height” Z (например, в подписи).
- Показать:
  - Земля в центре (точка/малый круг)
  - точка объекта
  - линия-вектор Earth→Object
  - подпись: id, t_utc, dist_ld, v_rel, mag
- Масштаб:
  - по умолчанию в LD (удобнее визуально), конвертировать AU→LD.

### Рендер (улучшение в Spec 1.1, если захотим)
Короткий трек ±N часов от close approach:
- Добавить запросы к Horizons (или иной источник) для получения RA/Dec/Δ на серии эпох (например, каждые 2 часа в пределах ±12 часов).
- Строить последовательность Earth→Object точек и соединять линией.

### API/Интеграция
- Pipeline (Python) добавляет в `alerts_neo.json` для каждого item:
  - `viz.encounter`:
    - `frame`: `"earth_equatorial"`
    - `t0_utc`: ISO
    - `r_au`: float
    - `xyz_au`: [x,y,z]
    - `dist_ld`: float (дублируем для удобства)
- Frontend (JS) добавляет режим карточки “Encounter View”:
  - миниатюра-иконка переключателя
  - canvas/WebGL/SVG рендер 2D

### Acceptance criteria
- Для каждого NEO item с `ra_deg/dec_deg/dist_au` рендерится корректная точка и вектор.
- Числа в подписи совпадают с JSON (dist, t, mag).
- Нет падений при отсутствии опциональных полей.

### Риски/границы
- Это “моментальная геометрия”, не орбита вокруг Земли.
- Для некоторых объектов RA/Dec могут быть геоцентрическими, а alt/az — топоцентрическими; не смешивать в расчётах.

## Spec 2 — NEO Heliocentric Orbit View (Earth orbit + object orbit)

Цель: построить **гелиоцентрическую орбиту** объекта (эллипс/гипербола) и сравнить с орбитой Земли в плоскости эклиптики, с отметкой положения на эпоху close approach.

### Пользовательская ценность
- Понять тип орбиты (Apollo/Amor/Aten и т.п. как следствие a/e/q/Q), наклон к эклиптике, геометрию пересечения с орбитой Земли.

### Входные данные (требуется добавить)
Для каждого NEO:
- Орбитальные элементы на эпоху:
  - `a` (AU), `e`, `i` (deg), `om`/Ω (deg), `w`/ω (deg), `ma`/M (deg), `epoch` (JD или ISO)
- Желательно:
  - `q`, `Q`, `tp` (если доступно)
  - качество/ковариация (если есть, хотя бы `condition_code`)

Источник:
- JPL SBDB API (предпочтительно) либо Horizons elements.

### Что меняем в pipeline
- Расширить сбор SBDB: сохранить `sbdb.elements` (как минимум 6 элементов + epoch).
- Сохранить также `sbdb.element_source`/`sbdb.orbit_class` при наличии.

### Вычисления (минимальная физика)
1. Генерация точек орбиты в перифокальной системе:
   - параметризация по истинной аномалии ν ∈ [0, 2π]
   - r(ν) = a(1-e²)/(1+e cos ν)
   - x_p = r cos ν, y_p = r sin ν, z_p = 0
2. Повороты в инерциальную (ecliptic/ICRF) систему:
   - R = Rz(Ω) * Rx(i) * Rz(ω)
   - [x,y,z] = R * [x_p, y_p, 0]
3. Орбита Земли:
   - упрощённо окружность радиуса 1 AU в плоскости эклиптики (для v1)
   - (улучшение) Earth position по de421/SPICE, чтобы отметить реальное положение Земли на t0
4. Положение объекта в момент close approach:
   - (v1) используем M(t0) через среднее движение n и разность эпох, решаем уравнение Кеплера → ν(t0) → r(t0)
   - (упрощение) если нет точной связки эпох, допускается отметить только “shape” орбиты без маркера t0.

### Рендер
- 2D в плоскости эклиптики (XY), с опциональным 3D toggle (показать z как цвет/высоту).
- Показать:
  - Солнце (0,0)
  - орбита Земли
  - орбита объекта
  - узлы (ascending/descending)
  - маркер текущего положения объекта на t0 (если вычислили)
  - подписи: a,e,i,MOID, dist at CA

### API/Интеграция
- В JSON:
  - `viz.orbit_helio`:
    - `frame`: `"helio_ecliptic"`
    - `elements`: {a,e,i_deg,Omega_deg,omega_deg,M_deg,epoch_jd}
    - `polyline_xy`: (опционально) предвычисленные точки
- В frontend:
  - новый режим “Orbit View”
  - кэширование полилинии по id+epoch, чтобы не считать каждый раз

### Acceptance criteria
- Для объектов с элементами строится орбитальная кривая (без NaN/провалов).
- Наклон i влияет на z (если 3D/height включен).
- Earth orbit отображается и масштаб сопоставим.

### Риски/границы
- Для близких пролётов важна точность эпохи и элементов; SBDB может давать элементы на другую эпоху.
- Для высокоэксцентричных/гиперболических траекторий нужно ограничивать диапазон ν, иначе рвётся масштаб.

## Spec 3 — NEOCP / Unconfirmed Candidates: Sky-track first, Orbit later

Цель: для NEOCP (неподтверждённые кандидаты) дать полезную визуализацию без ложного “орбитального” смысла: сначала трек на небе; затем (по готовности) попытка орбиты только при наличии элементов/векторов.

### Этап 3.1 — Sky-track (обязательный, доступен сразу)
Входные данные (уже есть):
- `ra_deg`, `dec_deg`, `mag`, `updated_utc`, `discovery` (дата)
Но сейчас это только “последняя точка”.

Что добавить в pipeline:
- Для top-N кандидатов (например, score>=X) сделать Horizons-запрос на серию эпох (например, каждые 1–2 часа на 24 часа вперёд).
- Получить:
  - RA/Dec(t)
  - (желательно) Δ(t) (range) и rate
  - (опционально) uncertainty если источник отдаёт

Рендер:
- проекция на небо: RA vs Dec с маркерами времени (градиент/подписи)
- подписи: mag, скорость углового движения, окно видимости по alt/az для наблюдателя

Acceptance criteria:
- Для выбранных кандидатов есть полилиния из N точек.
- В UI ясно, что это “путь на небе”, не орбита.

Риски:
- Наличие Horizons-эпемерид зависит от того, насколько объект определён; для свежих кандидатов может не работать.

### Этап 3.2 — Orbit (только если есть элементы/векторы)
Условия включения:
- В ответе SBDB/или другого источника есть элементы и они не “degenerate” (например, есть a,e,i,epoch).
- Иначе Orbit mode скрыт/disabled.

Рендер:
- Использовать тот же движок, что и Spec 2.

## Общие требования по качеству/UX

1. В интерфейсе всегда явно подписывать режим:
   - “Encounter (Earth-centered)”
   - “Orbit (Heliocentric)”
   - “Sky-track (RA/Dec)”
2. Всегда показывать источники и время актуальности:
   - `updated_utc`, `generated_utc`
3. Границы ответственности:
   - Encounter view не интерпретировать как орбиту вокруг Земли.
4. Производительность:
   - Предвычислять полилинии в pipeline там, где возможно.
   - В UI — кэш на уровне id+epoch.
